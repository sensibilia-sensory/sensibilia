# Institution-managed deployment and support operations

> This is the optional institution-managed stack: an institution-issued certificate and DNS name, reviewed images pinned by digest, and IT-owned backup monitoring. Most small laboratories should use the standard install and the [small-laboratory guide](standard.md) instead.

This guide supplies commands and configuration; it does not by itself approve a deployment for human collection. Use Linux containers on Linux Engine or Windows/macOS Docker Desktop. One Uvicorn worker serves production React assets and the API. The API has no published host port; Caddy exposes 443 and the HTTP-to-HTTPS redirect on the configured laboratory IP only. Uvicorn trusts forwarded headers only from TLS_PROXY_IP, the fixed Caddy address on PROXY_SUBNET, so HTTPS redirects retain the public origin. IT must select a subnet that does not overlap LAN/VPN/other Docker routes and must not attach untrusted containers. IT must also enforce the host/router firewall and prevent Internet forwarding.

## Release build and configuration

1. On the release builder, obtain reviewed immutable Node and Python **Debian slim** image references (tag plus sha256 digest). Python must be 3.13+; Node must satisfy the checked-in Vite lock. Supply them as NODE_IMAGE and PYTHON_IMAGE build arguments. Do not substitute unreviewed mutable tags. Dockerfile uses npm ci and requirements.lock, builds Python wheels, then copies assets and migrations into a non-root runtime. The application directory is read-only; /data is owned by UID/GID 10001. The installed wheel resolves static/migration files using SENSIBILIA_ROOT=/app.
2. Build and test each supported architecture separately. Example command shape: docker build --build-arg NODE_IMAGE=REVIEWED_NODE_DIGEST --build-arg PYTHON_IMAGE=REVIEWED_PYTHON_DIGEST -t REGISTRY_RELEASE . (one build context). Push only after the build/Compose/restore and platform tests pass, inspect the registry digest and archive it with the code revision and logs. Publish amd64/arm64 only where tested. No tested release digest is fabricated in the example file.
3. Copy deploy/lab.env.example to ignored deploy/private/lab.env. Replace both image placeholders with real tested @sha256 references. Set the reserved laboratory IP, stable institution DNS/SAN name, access-controlled secret files and an existing separate backup directory. Staff wrapper rejects mutable image tags. Backups are sensitive data; permissions/encryption/retention follow institutional policy.
4. Institution supplies PEM certificate chain/key and a researcher token of at least 32 characters. Never print tokens or put them in Git/image layers. Supply a separate operator key of at least 32 characters, different from the researcher key, for serving staff. Secret files are mounted read-only; the tokens are read through SENSIBILIA_RESEARCHER_TOKEN_FILE and SENSIBILIA_OPERATOR_TOKEN_FILE. Use either that or the existing SENSIBILIA_RESEARCHER_TOKEN, not both. Docker Desktop/host secret-file permissions must allow the mounted non-root application UID to read it; verify with a synthetic run. Certificate state persists on separate proxy volumes. This configuration loads institutional certificates; renewal is the named IT owner's job.
5. Use the named volume for DB/WAL/SHM together on the container filesystem. Never put the live DB on a network share. Prepare /backup as a separate destination, writable by UID 10001. On Desktop, select a host path outside the Docker VM disk. On Linux, use a different device; a second directory on the same disk is not an off-disk backup.
6. Run the staff shortcuts in runbook.md. Explicit initialize refuses an existing DB/sidecars. Neither API startup nor ordinary Start migrates. Wrong/missing Alembic revision prevents API startup; /health rechecks DB availability and the exact singleton expected revision, retaining its {status: ok} success body.

## Backup, scheduling and retention

Python sqlite3 online backup copies committed WAL content into a temporary self-contained DB. It checks integrity and foreign keys, records revision/table counts/release/SHA-256/time, flushes and renames the archive, then atomically updates last-success.json. A missing source is not silently created. Deadline failure leaves no completed copy. Archives contain credential hashes and all research data; do not expose the backup directory through HTTP.

The scheduler profile is a **short-lived job**, not a daemon: host scheduling invokes python scripts/laboratory.py backup. IT configures an hourly timer during collection, or nightly at 02:00 outside collection. Example cron entries (choose one; use absolute interpreter/release paths in the installed shortcut):

    0 * * * * /usr/bin/python3 /opt/sensibilia/scripts/laboratory.py backup
    0 2 * * * /usr/bin/python3 /opt/sensibilia/scripts/laboratory.py backup

On Windows, Task Scheduler invokes the same Python/script/backup arguments, starts in the release directory and runs under the Docker support account. Configure failed-job and missed-run alerts to the named owner; no messaging destination or scheduler was installed by this coding task. Daily staff Status verifies receipt/checksum/integrity and requires a backup within two hours. Nightly-mode monitor: docker compose --env-file deploy/private/lab.env --profile scheduler run --rm --no-deps backup python -m sensibilia.operations status --max-age-hours 26 (no additional arguments). Do not weaken collection checks to use nightly freshness.

After institutional retention approval, scheduled backup may add --retention to the staff command. It keeps the latest successful archive in 48 distinct UTC hourly buckets, 30 daily buckets and 12 monthly buckets (union). Multiple jobs within a bucket collapse to the latest. Pre-upgrade receipts are purpose=pre-upgrade and are retained until support explicitly releases them after the restore drill. Default backups never delete earlier copies. Do not run concurrent retention jobs; the host scheduler must serialize invocations. Replicate DB plus its matching JSON receipt encrypted off-disk daily; keep encryption keys separately and test the replication alert. Proposed RPO <=1 hour during collection, RTO <=2 hours remain targets until measured in a real restore drill.

## Upgrade and restore

The wrapper validates release digests, stops app and tls, verifies app has no running container, then invokes the maintenance profile with --no-deps. Upgrade requires the **previous** release digest so the pre-upgrade archive names the code that can restore that DB, while the new image runs Alembic. A failed backup/verification prevents Alembic; a failed migration has no automatic restart. Partial migration failure may leave changes: preserve the volume and restore the verified archive with the old image instead of assuming rollback. Maintenance does not start collection even on success.

Support restore selects the verified archive and matching image; target DB and WAL/SHM must all be absent. Configure a fresh named DATA_VOLUME, preserve the original volume, and use a separate config for the restore drill. Restore checks checksum, release, integrity, foreign keys and all table counts. After Start, compare frozen publication/packages, assignments, event UUIDs/causal ledgers, Data and CSV with the saved reconciliation. Test original-UUID duplicate retries without changing received timestamps. Record operator, duration, backup ID and exact release/device/origin; monthly and pre-upgrade drills are required. No delete-volume or blind downgrade command is provided.

## Verification boundary

Automated production browser tests: npm run build, then npm run test:deployment in frontend. The same flow-foundation.spec.ts runs authoring through offline profile restart, original UUID sync/retries, Data and CSV against production static files over HTTPS. The harness uses temporary migrated SQLite and an ephemeral self-signed OpenSSL certificate with explicit test-only trust bypass. This demonstrates HTTPS execution/cache/deep links, **not** institutional chain trust, Caddy execution, Docker volume behaviour or physical Android durability. The standard suite retains all gallery/density/axe checks. Full deployment acceptance still requires Linux/Desktop container install/upgrade/restore, certificate renewal, actual laboratory HTTPS/LAN and the physical-device gates in 013.

References: [Docker secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [SQLite online backup](https://sqlite.org/backup.html), [Caddy streaming proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

## Immutable stimulus files

Compose mounts laboratory_assets at /assets for app and maintenance/backup; ASSETS_VOLUME selects its name. Keep this named volume alongside laboratory_data when replacing containers. Local file-backed installations default to an assets directory beside the database; SENSIBILIA_ASSETS_DIRECTORY can set an explicit path. The API has no public asset-file mount. Never modify digest-named files, remove files to reclaim space, or migrate an operational database during development.

Backups with images have three inseparable parts: timestamp.db, timestamp.json, and timestamp.assets/ containing exact digest-named files. The receipt lists every digest/size in the database cut, including retained unused image references. Copy/replicate the whole set to the approved separate destination; verify/status and retention include files. A missing or changed file fails backup verification and prevents a successful maintenance precondition. Old image-free receipts remain valid.

Restore with both a fresh DATA_VOLUME and a fresh/empty ASSETS_VOLUME; preserve both failed volumes. If an explicit local assets directory is configured, point it at a fresh/empty restore directory. Restore refuses nonempty asset targets and verifies every file before reopening collection. Rehearse a real image package, compare digest/dimensions/alt text after preparation and offline restart, and reconcile pending response UUIDs. No Docker-volume/physical Android image-cache acceptance is claimed by the host automated tests.
